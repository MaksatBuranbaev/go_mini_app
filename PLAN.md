# Telegram Mini App: игра в го — план разработки

**Состояние:** фазы 0–8 сделаны и задеплоены, открытых пунктов нет. Комната —
`go-room.zenfonemaxprom124.workers.dev`, приложение — `t.me/ten_gen_bot/go_game`.

## 1. Что строим

Мини-апп для игры в го вдвоём с другом в реальном времени. Один игрок создаёт лобби, настраивает партию и отправляет ссылку второму. Ни аккаунтов, ни рейтинга, ни поиска соперника.

Границы MVP:
- доски 9×9 / 13×13 / 19×19, коми, фора (handicap), выбор цвета;
- полные правила: захваты, запрет самоубийства, ко (позиционный суперко), пас, сдача;
- завершение партии: два паса → отметка мёртвых камней → подсчёт очков;
- живая партия по WebSocket, контроль времени (Фишер + бёёми);
- лобби, приглашение по ссылке в личку или в группу;
- локальный архив партий и экспорт SGF.

Вне MVP: матчмейкинг, рейтинг, ИИ-оппонент, турниры, анализ партий, чат.

## 2. Архитектура

Постоянного сервера в проекте нет. Есть статика и **одна комната на партию** — Cloudflare Durable Object, к которому оба клиента подключаются по WebSocket.

```
Telegram WebView                Cloudflare
┌────────────────┐             ┌──────────────────────────────┐
│  apps/web      │  HTTPS      │  Pages (статика)             │
│  React+Canvas  │◄───────────►│                              │
│  go-engine     │             ├──────────────────────────────┤
│  (предсказание │  WebSocket  │  Worker → Durable Object     │
│   хода)        │◄───────────►│  комната = партия            │
└────────────────┘             │  go-engine (тот же пакет)    │
                               │  storage: ходы, часы         │
                               │  alarm(): просрочка времени  │
                               └──────────────────────────────┘
```

Почему именно так:

- **Durable Object — правильная единица.** Одна партия = один объект с собственным состоянием и собственным адресом, без блокировок и гонок. Никакой БД, никакого Redis, никакого pub/sub: соперники по определению попадают в один и тот же объект. Побочная выгода вскрылась в фазе 6: запросы к объекту сериализованы, поэтому «оба открыли ссылку одновременно» разрешается само собой — место достаётся первому, второй становится наблюдателем.
- **Судья появляется бесплатно.** Движок правил написан на TypeScript и запускается в Workers-рантайме без изменений — тот же пакет, что в браузере. Клиент отрисовывает ход оптимистично, комната его валидирует и подтверждает. Чит модифицированным клиентом закрыт.
- **Hibernation решает главную проблему го.** Игрок думает над ходом минутами, приложение уходит в фон. WebSocket Hibernation API (`state.acceptWebSocket()`) держит соединение, пока объект выгружен из памяти, и не тарифицирует простой. Плата за это одна: **состояние обязано жить в `storage`, а не в полях класса** — после гибернации память пуста. Это ключевое ограничение всего дизайна комнаты.
- **`storage.setAlarm()` — таймкипер.** Просрочка времени фиксируется по будильнику на дедлайн текущего хода, даже если оба клиента отключены. Без этого «победа по времени» в асинхронной партии не работает.
- **Эксплуатации нет.** Деплой из git, логи в дашборде, сервера, за которым надо следить, не существует.

Приглашение при этом становится тривиальным: в deep link едет только id комнаты, настройки партии лежат в самой комнате. Кодек состояния в URL не нужен.

**Про тариф.** Проект целится в бесплатный план Workers: 100 000 запросов в сутки, 10 мс процессорного времени на вызов. Каждое WS-сообщение в спящую комнату считается запросом. Партия обходится примерно в два запроса на ход плюс подключения — периодической синхронизации часов в реализации нет намеренно (§5.4), поэтому счётчик не тикает, пока никто не ходит. Durable Objects на бесплатном плане доступны в SQLite-варианте. Превышение лимита на Free не тарифицируется, а отдаёт ошибку, так что неожиданного счёта быть не может. Workers Paid ($5/мес, 10 млн запросов) понадобится, только если приложение выйдет за пределы дружеского круга. Статика на Pages бесплатна независимо от трафика.

Если Cloudflare по каким-то причинам не подходит, тот же дизайн один в один ложится на PartyKit; запасной вариант потяжелее — Node + Socket.IO на Fly.io, но тогда возвращаются вопросы эксплуатации.

## 5. Комната (`apps/room`)

### 5.1 Состояние в `storage`
```ts
meta    : { roomId, createdAt, settings }
seats   : { black?: { userId, name }, white?: { userId, name } }
status  : 'waiting' | 'playing' | 'scoring' | 'finished'
m:NNNNNN: { seq, color, type: 'play'|'pass'|'resign', x?, y?, timeLeftMs, at }
clock   : { blackMs, whiteMs, lastMoveAt, blackPeriods, whitePeriods }
scoring : { dead, acceptedBy }
undo    : { by, seq } — висящая просьба вернуть ход, см. §11
result  : 'B+12.5' | 'W+R' | 'B+T' | …
```
Позиция на доске **не хранится** — она восстанавливается прогоном ходов через движок при пробуждении объекта. Одно место истины, рассинхрон структурно невозможен.

Оговорка от лимита в 10 мс процессорного времени на бесплатном плане: каждые ~50 ходов кладём в `storage` снапшот позиции с Zobrist-хешем и историей ко, чтобы после гибернации не переигрывать партию с первого хода. Снапшот — производный кэш, источник истины остаётся списком ходов.

Отдельное правило прогона: **ход после двух пасов означает возврат из подсчёта**. «Доиграть» отдельной записью не сохраняется, о нём говорит сам факт продолжения. Без этого запись доигранной партии не воспроизводится вовсе, и комната ломается на первой же выгрузке из памяти.

### 5.2 Посадка за доску
`initData` проверяется в Worker'е HMAC-подписью с `BOT_TOKEN` (секрет Worker'а). Первые два уникальных Telegram-id занимают места чёрных и белых согласно настройкам лобби, дальше место закреплено: переподключение возвращает игрока на его сторону. Пришедший по ссылке, когда мест нет, становится **наблюдателем**: видит всю партию в реальном времени, но ходить, пасовать, сдаваться и размечать мёртвых не может. Игроки видят число зрителей.

### 5.3 Протокол

HTTP: `POST /rooms` (создать комнату с настройками → id), `GET /rooms/:id` (превью для экрана приглашения), `GET /rooms/:id/sgf` (запись партии).

WS, клиент → комната: `join {lastSeq}`, `move {x, y, seq}`, `pass {seq}`, `resign`, `scoring:toggle {point}`, `scoring:accept`, `scoring:resume`, `undo:request`, `undo:answer {accept}`, `undo:cancel`.

WS, комната → клиент: `state` (полный снапшот), `sync` (дельта на реконнект), `move`, `clock`, `scoring`, `over`, `undo`, `presence`, `error`.

Идемпотентность: клиент присылает ожидаемый номер хода `seq`; при несовпадении комната отвечает полным `state` вместо `move`. Это закрывает двойные тапы и повторы после разрыва. Reconnect работает так же: `join {lastSeq}` → дельта или снапшот.

Все payload'ы описаны zod-схемами в `packages/protocol` и валидируются обеими сторонами.

### 5.4 Часы
Комната хранит `blackMs`, `whiteMs`, `lastMoveAt`, счётчики периодов бёёми. Дедлайн текущего хода = `lastMoveAt + timeLeft`, на него ставится `storage.setAlarm()`, сбрасываемый каждым ходом. Просрочка фиксируется будильником независимо от того, подключён ли кто-нибудь.

Периодической синхронизации часов **нет намеренно**: она будила бы объект всю партию ради тиканья секунд, против того, ради чего в §2 выбрана гибернация. Показания едут с каждым ходом, при старте партии и на подключении, между ними клиент досчитывает сам. Расхождение системных часов телефона снимается полем `serverNow` в каждом сообщении о часах — без этого телефон, ушедший на пару минут, показывает чужое время.

Клиент не имеет права врать в свою пользу: пока свой ход не подтверждён комнатой, часы на экране идут у ходившего, а не у соперника. Ход, оставшийся без ответа три секунды, поднимает предупреждение и переподключение.

## 6. Движок правил (`packages/go-engine`)

Чистые детерминированные функции, ноль зависимостей и ноль I/O — иначе он не запустится в Workers:
- позиция — `Uint8Array(n*n)`, поиск групп и дамэ — flood fill с переиспользуемым буфером;
- ход: постановка → снятие групп противника без дамэ → проверка самоубийства → проверка повтора позиции;
- повторы — **Zobrist-хеш** позиции плюс `Set` истории (позиционный суперко); простое ко — частный случай;
- `play()` возвращает `Result<NextPosition, IllegalMoveReason>`, без исключений;
- подсчёт — **китайские правила (area scoring)**; японские добавляются в §10.1;
- SGF: парсер и сериализатор для экспорта и для тестов. Коми чужих экспортёров (`KM[650]`, запятая вместо точки) разбирается в `parseKomi`.

Тесты: юнит-кейсы на ко, суперко, самоубийство, углы и края + прогон открытого SGF-корпуса с утверждением «ни одного нелегального хода, итоговый счёт совпадает с записанным».

## 7. Фаза подсчёта

Слабое место любой реализации го — определение мёртвых камней, без движка уровня KataGo оно не автоматизируется. Поэтому:
1. Два паса подряд → статус `scoring`.
2. Оба игрока тапами помечают мёртвые группы, отметки транслируются обоим в реальном времени. Любая правка снимает согласие обеих сторон.
3. Оба нажали «принять» → счёт по выбранной системе плюс коми, партия закрыта.
4. Не согласились → кнопка «доиграть», возврат в `playing` с сохранением истории.
5. Первичная догадка о мёртвых группах — простая эвристика, строго как подсказка; решают игроки.

Подсветка территории на экране считается тем же кодом, что и итог: разойтись они не могут по построению.

## 8. UX внутри Telegram

- Постановка камня в два тапа: первый — призрачный камень с увеличенной подсветкой, второй по той же точке — подтверждение. Палец на 19×19 накрывает 3×3 пересечения, одиночный тап без подтверждения даст промахи. Отдельной кнопки подтверждения нет: она занимала низ экрана и двигала вьюпорт между тапами, из-за чего второй тап улетал в соседнее пересечение.
- Зум и пан по доске для 19×19 на маленьком экране.
- `HapticFeedback` и звук на постановку камня и на захват группы; снятые камни исчезают анимацией — захват меняет доску не там, куда смотрит палец.
- `MainButton` контекстна: «Позвать друга» / «Принять счёт» / «Пас» на одном устройстве. Во время партии по сети она пуста — см. первый пункт.
- `BackButton` — выход в лобби, с подтверждением при активной партии.
- Тема из `themeParams`, светлая и тёмная; вёрстка по высоте вьюпорта, экраны прокручиваются сами: полагаться на прокрутку документа в WebView нельзя.
- `disableVerticalSwipes()` — иначе свайп по доске сворачивает приложение.
- Лобби: размер доски, фора, цвет, коми, система правил, контроль времени, звук, «Пригласить друга», «На одном устройстве», «Мои партии».
- Отправка приглашения: `openTelegramLink('https://t.me/share/url?url=' + link)` — штатная шторка выбора чата, без inline-режима и без кода на стороне бота.
- Открытие по ссылке сразу показывает настройки партии и одну кнопку — «Принять» либо «Смотреть партию», если мест уже нет.
- Индикатор присутствия соперника («в сети» / «отошёл») и число зрителей.
- Разрыв связи виден сразу: полоса поверх доски с кнопкой, а когда показывать ещё нечего — целый экран «Нет связи». Про сеть спрашиваем систему, а не сокет: сокет, в который никто не пишет, выглядит живым до таймаута TCP.

## 10. Фаза 7

Пять пунктов от игрока плюс один долг по инструментам. Первые два меняют правила и требуют движка, остальные — вид и ощущение.

### 10.1 Японские правила и выбор системы подсчёта

Сейчас счёт всегда китайский (area scoring): очки — свои камни на доске плюс окружённая территория. Японский считает иначе: **территория плюс пленные**, свои камни не считаются.

Что нужно сделать:
- `rules: 'chinese' | 'japanese'` в `GameSettings`, выбор в лобби, хранение в комнате, запись в SGF (`RU[Chinese]` / `RU[Japanese]`).
- `scoreTerritory(state, dead)` в движке рядом с существующим `scoreArea`. Пленные — это захваченные за партию камни (движок их уже считает) плюс отмеченные мёртвыми в фазе подсчёта: они уходят в плен сопернику, а их пункты становятся территорией.
- Общая карта владельцев для подсветки, зависящая от системы: инвариант «подсветка не расходится с итогом» должен сохраниться для обеих.
- Коми по умолчанию: японские 6.5, китайские 7.5, с форой — 0.5. Пересчитывается при смене системы, пока игрок не задал коми руками (§10.2).

Что честно сказать заранее:
- **Сэки.** В японских правилах территория в сэки не считается никому, а распознавать сэки движок не умеет. Первым приближением не засчитываем территорией пустые пункты, соседствующие с живыми группами обоих цветов — это ровно случай сэки-дамэ. Типовое сэки покрывается, экзотика — нет; это честнее, чем считать сэки территорией.
- **Ко.** Официальные японские правила используют простое ко и «нет результата» при тройном ко. У нас позиционный суперко для обеих систем — осознанное отклонение: суперко строже, спорных позиций не создаёт, запись остаётся легальной для любого просмотрщика.
- **На игру выбор не влияет,** только на итог. Разница в том, что в китайских правилах доигрывание внутри своей территории бесплатно, а в японских каждый лишний ход стоит очко.

Критерий готовности: партия, доигранная до конца, даёт результат, совпадающий с ручным подсчётом по обеим системам; в SGF пишется `RU[]`; экран подсчёта показывает то же, что попадёт в результат.

### 10.2 Коми задаётся руками

Сейчас коми выводится из размера доски и форы, игрок его не выбирает.

- В лобби — шаг −/+ 0.5 в диапазоне −10…+10, стартовое значение прежнее автоматическое.
- Автоподстановка перестаёт работать, как только игрок тронул коми руками: иначе смена размера доски молча затрёт его выбор.
- В схеме `GameSettings` — проверка «кратно 0.5 и в диапазоне». Сейчас туда пролезет любое число, включая дробное с четвертью.

### 10.3 Время по длительности партии

Пресеты назывались по контролю («Блиц 5+5», «Фишер 10+10») — это ничего не
говорило о том, сколько игрок просидит за партией. Стало: подпись-оценка мелким
курсивом, под ней ступень из двух вариантов одной длины, у выбранного — обводка
и точка.

```
~ 5 мин
[ 30 сек + 5 сек ] •   [ 30 сек + 5×10 сек ]

~ 10 мин
[ 2 мин + 7 сек ]      [ 2 мин + 5×15 сек ]
```

- **Лестница своя у каждой доски.** Одни и те же секунды — это блиц на 9×9 и
  полтора часа на 19×19, поэтому меняется не подпись, а сами контроли:
  9×9 — 5/10/20 минут, 13×13 — 10/20/30, 19×19 — 20/40/час.
- Оценка считается, а не подписывается руками: 2 × (основное + добавка × ходов
  на игрока), ходов на игрока по доске — 25 / 55 / 110. Период бёёми входит
  долей 0.6: целиком его досиживают редко, а верхняя граница пугает вместо
  того, чтобы помогать. Итог округляется до круглого — «~ 27 мин» показывать
  незачем.
- В ступени два варианта: с добавкой и с бёёми. Они по построению близки по
  длине (юнит-тест держит расхождение в пределах четверти), поэтому подпись у
  них одна.
- Выбор хранится как «ступень + вид контроля», а не номер в общем списке: при
  смене доски игрок остаётся на партии той же длины и того же вида.
- «Без часов» — последняя ступень с подписью «Сколько понадобится».

### 10.4 Настоящий звук камня

Стучит запись, а не синтез. Файл — [baduk2](https://freesound.org/s/840425/)
с freesound под **CC0**: лицензия здесь не формальность, звук лежит в
репозитории. Подробности и пересборка — `tools/sound/README.md`.

- В записи два десятка ударов; `tools/sound/slice.mjs` находит их по огибающей
  и складывает пять чистых в один файл по 130 мс на ячейку (56 КиБ, укладываемся
  в бюджет). Декодирует mp3 сам браузер — ffmpeg в окружении нет, а headless
  Edge для прогонов и так поднят.
- Ход берёт случайную ячейку с разбросом высоты ±3% и громкости ±10%: серия
  ходов не должна звучать метрономом. Захват — тот же стук плюс три тихих
  вразнобой, будто камни сгребают в чашу.
- Файл подтягивается лениво, первым же тапом, и до декодирования (а также если
  он не доехал) звучит прежний синтез — стук просто становится беднее.
- **Звук — только про камень.** Пас стучал камнем, которого не было, и это
  сбивало с толку: теперь у паса только отклик в руку, а разметка мёртвых в
  подсчёте молчит и подавно.

### 10.5 Фон лобби

Лобби было плоской простынёй, а в тёмной теме телефона — ещё и нечитаемым.
Причина оказалась не в фоне: **telegram-ui не знал, что тема тёмная.**
Палитру клиент отдаёт переменными, но часть значений (обводки, надписи кнопок
в режиме outline, разделители) библиотека держит в своей теме, и без явного
`appearance` она оставалась светлой. На телефоне это выглядело так: подложки и
текст пришли тёмные, а надписи кнопок остались чёрными на тёмном — то есть
невидимыми. Теперь тему выставляет `telegram/Themed.tsx`, он же кладёт признак
на `<html>` для собственного CSS.

Остальное — вид:

- Тёплая подложка в тон доске поверх цвета темы. В тёмной теме Telegram шлёт
  `secondary` **светлее** `bg`, из-за чего карточки проваливались в фон:
  подложку затемняем, чтобы порядок был как в светлой — секции лежат на фоне,
  а не в нём.
- Карточки лобби — тёплая бумага: цвет здесь свой, а не клиентский. Текст
  остаётся клиентским, и он в любой светлой теме тёмный, в любой тёмной —
  светлый, так что читаемость не зависит от чужой темы.
- Заголовок секции клиент присылает акцентным (в тёмной теме — ярко-синим), и
  той же переменной telegram-ui красит подписи под секцией. Половина лобби
  выглядела ссылками — вернули приглушённый цвет.
- Свои элементы (часы, статус, пилюли времени) получили шрифт: telegram-ui
  держит его в переменной и ставит только своим компонентам, а браузер рисовал
  наши с засечками.
- Контраст проверяется прогоном, а не на глаз: `lobby.mjs` открывает лобби с
  настоящей тёмной палитрой мобильного Telegram (`?dev_theme=dark` в моке) и
  требует, чтобы надпись кнопки была светлее карточки.
- Строка про ко из лобби убрана: она ничего не настраивала — правило одно и то
  же в любой партии, — а место занимала наравне с настройками.

### 10.6 Прогоны переезжают в репозиторий

Сделано: `tests/` с общей гарнитурой (`lib/`), README и `run-all.sh`.
Тринадцать прогонов — двенадцать в общем списке плюс отдельный на выгрузку
комнаты, который убивает процесс воркера и потому запускается сам по себе.

## 11. Отмена хода

Промах по пересечению стоит партии, а «переходить» в го не принято — поэтому
отмена сделана просьбой, а не правом.

- Просить можно только о **своём последнем** ходе и только пока он последний:
  иначе просьба стала бы способом отобрать у соперника его ход.
- Соперник отвечает «разрешить» или «отказать»; просивший может передумать
  сам. Ход соперника снимает висящую просьбу — отменять уже нечего.
- Откат делает комната: убирает ход из записи, откатывает номер и рассылает
  полный снапшот. Дельтой это не выразить — ходов становится меньше, а не
  больше.
- Часы: потраченное время не возвращается, оно шло на самом деле. А добавка
  Фишера снимается — иначе отмена собственного хода была бы способом копить
  время. Сгоревшие периоды бёёми остаются сгоревшими.
- Снапшот позиции, снятый на отменённом ходу, удаляется. Он сходится сам с
  собой по хешу и потому пережил бы проверку — а после нового хода с тем же
  номером комната подняла бы из него позицию из другой партии.
- За одним устройством спрашивать некого: ход снимается сразу, а позиция
  пересобирается прогоном записи с начала. Держать стек состояний ради одной
  кнопки дороже, чем переиграть партию, которая целиком лежит рядом.
- В подсчёте отмены нет: для возврата к игре есть «доиграть».

## 12. Инварианты

Риски, из-за которых дизайн выбран таким, и то, чем каждый из них закрыт. Прогоны названы по именам файлов (§10.6).

| Инвариант | Чем держится | Чем проверяется |
|---|---|---|
| Гибернация не ломает партию | Всё состояние в `storage`, поля класса — кэш; метаданные сокета через `serializeAttachment` | `hibernate.mjs`: партия из 60 ходов, процесс воркера убивается, партия продолжается с 61-го |
| Разрыв WS не теряет ход и не завершает партию | `partysocket` с бэкоффом, `join {lastSeq}` → дельта, партия закрывается только часами | `sync.mjs`: ход при мёртвом сокете, реконнект, доски сходятся попиксельно |
| Клиент не расходится с комнатой | Судья — комната; при несовпадении `seq` приходит полный `state` | `protocol.mjs`, `sync.mjs` |
| Часы не врут в пользу клиента | Своё время идёт до подтверждения хода; сдвиг системных часов снимается через `serverNow` | `skew.mjs`: вкладка на три минуты в будущем видит то же, что соперник |
| Просрочка срабатывает без клиентов | `storage.setAlarm()` на дедлайн | `endgame.mjs`: партия закрывается `W+T` без единого хода |
| Подсветка территории = итог | Одна и та же функция для экрана и для счёта | юнит-тесты движка |
| Запись партии полная | Пас рассылается как ход; ход после двух пасов означает возврат из подсчёта | `archive.mjs`, `endgame.mjs`, юнит-тест движка на прогон записи |
| Наблюдатель не вмешивается | Место проверяется в комнате, а не в интерфейсе | `watch.mjs`: ход, пас, сдача и разметка от зрителя отбиты |
| `BOT_TOKEN` не утекает | Только секрет Worker'а, никогда в бандле; проверка `initData` исключительно в комнате | `protocol.mjs`: подпись чужим токеном отвергается |
| Уведомления не ломают ход | 403 от Bot API — штатный исход, глушится | `sgf.mjs` |
| Тёмная тема клиента не ломает читаемость | Тема telegram-ui выставляется явно из `isMiniAppDark`; поверхности лобби со своим контрастом | `lobby.mjs`: надпись кнопки светлее карточки под палитрой мобильного Telegram |
| Звук — только про поставленный камень | Пас и разметка мёртвых идут мимо `stoneSound` | `polish.mjs`: счётчик источников звука не меняется на пасе и в подсчёте |
| Отменяется только свой последний ход | Комната сверяет цвет последнего хода и его номер, согласие даёт соперник | `undo.mjs`: чужой ход, протухшая просьба и просьба зрителя отбиты |
| Откат не рождает время | Вместе с ходом снимается добавка Фишера | юнит-тесты часов, `undo.mjs` |

Отдельно: **промахи по пересечениям на 19×19** закрыты двухтаповым подтверждением, увеличенной зоной хит-теста, зумом и паном; автоматического определения мёртвых камней мы не обещаем — только подсказка и согласование.
