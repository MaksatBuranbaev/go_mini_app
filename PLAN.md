# Telegram Mini App: игра в го — план разработки

## 1. Что строим

Мини-апп для игры в го вдвоём с другом в реальном времени. Один игрок создаёт лобби, настраивает партию и отправляет ссылку второму. Ни аккаунтов, ни рейтинга, ни поиска соперника.

Границы MVP:
- доски 9×9 / 13×13 / 19×19, коми, фора (handicap), выбор цвета;
- полные правила: захваты, запрет самоубийства, ко (позиционный суперко), пас, сдача;
- завершение партии: два паса → отметка мёртвых камней → подсчёт очков;
- живая партия по WebSocket, контроль времени (Фишер + бёёми);
- лобби, приглашение по ссылке в личку или в группу;
- локальный архив партий и экспорт SGF.

Вне MVP: матчмейкинг, рейтинг, ИИ-оппонент, турниры, анализ партий, чат.

## 2. Архитектура

Постоянного сервера в проекте нет. Есть статика и **одна комната на партию** — Cloudflare Durable Object, к которому оба клиента подключаются по WebSocket.

```
Telegram WebView                Cloudflare
┌────────────────┐             ┌──────────────────────────────┐
│  apps/web      │  HTTPS      │  Pages (статика)             │
│  React+Canvas  │◄───────────►│                              │
│  go-engine     │             ├──────────────────────────────┤
│  (предсказание │  WebSocket  │  Worker → Durable Object     │
│   хода)        │◄───────────►│  комната = партия            │
└────────────────┘             │  go-engine (тот же пакет)    │
                               │  storage: ходы, часы         │
                               │  alarm(): просрочка времени  │
                               └──────────────────────────────┘
```

Почему именно так:

- **Durable Object — правильная единица.** Одна партия = один объект с собственным состоянием и собственным адресом, без блокировок и гонок. Никакой БД, никакого Redis, никакого pub/sub: соперники по определению попадают в один и тот же объект.
- **Судья появляется бесплатно.** Движок правил написан на TypeScript и запускается в Workers-рантайме без изменений — тот же пакет, что в браузере. Клиент отрисовывает ход оптимистично, комната его валидирует и подтверждает. Чит модифицированным клиентом закрыт.
- **Hibernation решает главную проблему го.** Игрок думает над ходом минутами, приложение уходит в фон. WebSocket Hibernation API (`state.acceptWebSocket()`) держит соединение, пока объект выгружен из памяти, и не тарифицирует простой. Плата за это одна: **состояние обязано жить в `storage`, а не в полях класса** — после гибернации память пуста. Это ключевое ограничение всего дизайна комнаты.
- **`storage.setAlarm()` — таймкипер.** Просрочка времени фиксируется по будильнику на дедлайн текущего хода, даже если оба клиента отключены. Без этого «победа по времени» в асинхронной партии не работает.
- **Эксплуатации нет.** Деплой из git, логи в дашборде, сервера, за которым надо следить, не существует.

Приглашение при этом становится тривиальным: в deep link едет только id комнаты, настройки партии лежат в самой комнате. Кодек состояния в URL не нужен.

**Про тариф.** Проект целится в бесплатный план Workers: 100 000 запросов в сутки, 10 мс процессорного времени на вызов. Каждое WS-сообщение в спящую комнату считается запросом, партия в го — порядка тысячи сообщений вместе с синхронизацией часов, то есть потолок примерно сотня партий в день. Для игры с друзьями это с огромным запасом. Durable Objects на бесплатном плане доступны в SQLite-варианте — сверить перед фазой 3 стоит только сам факт доступности в дашборде. Превышение лимита на Free не тарифицируется, а отдаёт ошибку, так что неожиданного счёта быть не может. Workers Paid ($5/мес, 10 млн запросов) понадобится, только если приложение выйдет за пределы дружеского круга. Статика на Pages бесплатна независимо от трафика.

Если Cloudflare по каким-то причинам не подходит, тот же дизайн один в один ложится на PartyKit; запасной вариант потяжелее — Node + Socket.IO на Fly.io, но тогда возвращаются вопросы эксплуатации.

## 5. Комната (`apps/room`)

### 5.1 Состояние в `storage`
```ts
meta    : { id, createdAt, settings, seats: { black?: tgId, white?: tgId } }
status  : 'waiting' | 'playing' | 'scoring' | 'finished'
moves[] : { seq, color, type: 'play'|'pass'|'resign', x?, y?, timeLeftMs, at }
clock   : { blackMs, whiteMs, lastMoveAt, blackPeriods, whitePeriods }
scoring : { deadGroups, acceptedBy }
result  : 'B+12.5' | 'W+R' | 'B+T' | …
```
Позиция на доске **не хранится** — она восстанавливается прогоном `moves` через движок при пробуждении объекта. Одно место истины, рассинхрон структурно невозможен.

Оговорка от лимита в 10 мс процессорного времени на бесплатном плане: каждые ~50 ходов кладём в `storage` снапшот позиции с Zobrist-хешем и историей ко, чтобы после гибернации не переигрывать партию с первого хода. Снапшот — производный кэш, источник истины остаётся списком ходов; при несовпадении хеша он просто выбрасывается и позиция считается заново.

### 5.2 Посадка за доску
`initData` проверяется в Worker'е HMAC-подписью с `BOT_TOKEN` (секрет Worker'а) — берём `@telegram-apps/init-data-node` в варианте на Web Crypto либо включаем `nodejs_compat`. Первые два уникальных Telegram-id занимают места чёрных и белых согласно настройкам лобби, дальше место закреплено: переподключение возвращает игрока на его сторону, посторонний со ссылкой сесть за доску уже не может (позже — сможет смотреть).

### 5.3 Протокол

HTTP: `POST /rooms` (создать комнату с настройками → id), `GET /rooms/:id` (превью для экрана приглашения), `GET /rooms/:id/sgf`.

WS, клиент → комната: `join {lastSeq}`, `move {x, y, seq}`, `pass {seq}`, `resign`, `scoring:toggle {point}`, `scoring:accept`, `scoring:resume`.

WS, комната → клиент: `state` (полный снапшот), `move`, `clock`, `scoring`, `over`, `presence`, `error`.

Идемпотентность: клиент присылает ожидаемый номер хода `seq`; при несовпадении комната отвечает полным `state` вместо `move`. Это закрывает двойные тапы и повторы после разрыва. Reconnect работает так же: `join {lastSeq}` → дельта или снапшот.

Все payload'ы описаны zod-схемами в `packages/protocol` и валидируются обеими сторонами.

### 5.4 Часы
Комната хранит `blackMs`, `whiteMs`, `lastMoveAt`, счётчики периодов бёёми. Дедлайн текущего хода = `lastMoveAt + timeLeft`, на него ставится `storage.setAlarm()`, сбрасываемый каждым ходом. Клиент только интерполирует и раз в ~10 секунд сверяется по событию `clock`. Просрочка фиксируется будильником независимо от того, подключён ли кто-нибудь.

## 6. Движок правил (`packages/go-engine`)

Чистые детерминированные функции, ноль зависимостей и ноль I/O — иначе он не запустится в Workers:
- позиция — `Uint8Array(n*n)`, поиск групп и дамэ — flood fill с переиспользуемым буфером;
- ход: постановка → снятие групп противника без дамэ → проверка самоубийства → проверка повтора позиции;
- повторы — **Zobrist-хеш** позиции плюс `Set` истории (позиционный суперко); простое ко — частный случай;
- `play()` возвращает `Result<NextPosition, IllegalMoveReason>`, без исключений;
- подсчёт — **китайские правила (area scoring)**: проще считаются и прощают доигрывание;
- SGF: парсер и сериализатор для экспорта и для тестов.

Тесты: юнит-кейсы на ко, суперко, самоубийство, углы и края + прогон ~1000 партий из открытого SGF-корпуса с утверждением «ни одного нелегального хода, итоговый счёт совпадает с записанным». Фаза автономна — пишется и проверяется без Telegram и без Cloudflare.

## 7. Фаза подсчёта

Слабое место любой реализации го — определение мёртвых камней, без движка уровня KataGo оно не автоматизируется. Поэтому:
1. Два паса подряд → статус `scoring`.
2. Оба игрока тапами помечают мёртвые группы, отметки транслируются обоим в реальном времени.
3. Оба нажали «принять» → счёт по area scoring плюс коми, партия закрыта.
4. Не согласились → кнопка «доиграть», возврат в `playing` с сохранением истории.
5. Первичная догадка о мёртвых группах — простая эвристика (группа без места для двух глаз внутри области противника), строго как подсказка; решают игроки.

## 8. UX внутри Telegram

- Постановка камня в два тапа: первый — призрачный камень с увеличенной подсветкой, второй (или `MainButton`) — подтверждение. Палец на 19×19 накрывает 3×3 пересечения, одиночный тап без подтверждения даст промахи.
- Зум и пан по доске для 19×19 на маленьком экране.
- `HapticFeedback` на постановку камня и на захват группы.
- `MainButton` контекстная: «Подтвердить ход» / «Пас» / «Принять счёт».
- `BackButton` — выход в список партий, с `showConfirm` при активной партии.
- Тема из `themeParams`, светлая и тёмная; верстка по `viewportStableHeight`.
- `disableVerticalSwipes()` — иначе свайп по доске сворачивает приложение.
- Лобби: размер доски, коми (пресет по размеру), фора, цвет (чёрные / белые / случайно), контроль времени, кнопка «Пригласить друга».
- Отправка приглашения: `openTelegramLink('https://t.me/share/url?url=' + link)` — штатная шторка выбора чата, без inline-режима и без кода на стороне бота.
- Открытие по ссылке сразу показывает настройки партии и одну кнопку «Принять».
- Индикатор присутствия соперника («в сети» / «отошёл») — иначе непонятно, ждать хода или нет.

| # | Фаза | Критерий готовности |
|---|---|---|
| 0 | Каркас | pnpm-монорепо; Vite + React + Telegram SDK на Cloudflare Pages; пустой Worker с DO задеплоен; приложение зарегистрировано в BotFather, открывается в Telegram, читает `start_param` и пингует комнату. |
| 1 | Движок правил | `packages/go-engine`: захваты, суицид, суперко, подсчёт, SGF. Зелёный прогон SGF-корпуса. UI ещё нет. |

| 3 | Живая комната | DO с `storage` и hibernation, проверка `initData`, посадка за доску, лобби → ссылка → присоединение, партия между двумя устройствами, авторитетная валидация ходов, reconnect по `lastSeq`, presence. **Первая играбельная версия вдвоём.** |
| 4 | Часы и завершение | Фишер и бёёми, `setAlarm()` на просрочку, пас, сдача, фаза отметки мёртвых камней с согласованием, подсчёт, результат. |

Ориентир: фазы 1 и 4 съедят больше времени, чем кажется — суперко и подсчёт недооценивают всегда. Фаза 3 упирается не в объём кода (комната — порядка 300 строк), а в отладку внутри Telegram WebView.

## 10. Риски

| Риск | Митигация |
|---|---|
| Гибернация стирает память объекта | Всё состояние — только в `storage`, поля класса считаются кэшем; метаданные сокета — через `serializeAttachment`. Тест: принудительная выгрузка объекта посреди партии. |
| Разрывы WS в мобильном WebView | `partysocket` с бэкоффом, восстановление по `join {lastSeq}`, реконнект по `visibilitychange`; партия не завершается по дисконнекту — только по часам. |
| Лимиты и тариф Durable Objects | Сверить с актуальным прайсом до фазы 3; при необходимости Workers Paid $5/мес; дизайн переносим на PartyKit без переписывания. |
| Холодный старт комнаты | Первый `join` может ждать пробуждения объекта — показывать скелетон доски, а не пустой экран. |
| Подсчёт мёртвых камней | Китайские правила + ручная отметка с согласованием и кнопкой «доиграть». Полную автоматизацию не обещаем. |
| Промахи по пересечениям на 19×19 | Двухтаповое подтверждение, увеличенная зона хит-теста, зум и пан. |
| Утечка `BOT_TOKEN` | Только секрет Worker'а, никогда в бандле `apps/web`; проверка `initData` исключительно в комнате. |
| Уведомления не доходят | Бот может писать только тем, кто его запускал; 403 логируем и молчим, на UX не завязываемся. |

## 12. После MVP

ИИ-оппонент на WASM-движке прямо в браузере (для 9×9 реально и без нагрузки на комнату), задачи-тэсудзи, разбор партии с вариациями, наблюдение за живой партией из группового чата, японский подсчёт, импорт чужих SGF для просмотра.
